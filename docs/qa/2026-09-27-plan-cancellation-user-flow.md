# 计划取消与完整闭环验证（2026-09-27）

本次实现已在本地数据库和 iOS 模拟器验证。未发布到线上，未改动生产数据库。

## 已实现的体验

- 聊天中的计划卡片右上角 `⋯`：发起人可撤回待回应提议；已确认、尚未结束的计划，双方均可取消。
- 取消需要确认。开始前不足 2 小时（含进行中）必须选择原因；其他情况原因选填，补充说明最多 240 字。明确提示原因会展示给对方。
- 取消已确认计划：双方日历同步移除，计划归入「已结束」，聊天保留取消记录、原因与说明，可以继续发消息。
- 撤回改期提议：原先已确认的时间及双方日历保持不变。
- 对方收到应用内弹窗，显示取消者、活动、时间，可「查看详情」或「知道了」。查看详情定位到聊天内对应的计划卡片。
- 未读提醒持久化；应用恢复前台时补取。前台每 15 秒补取一次，也响应推送。用户确认后服务端标为已读；确认请求失败时保留本地待同步记录，避免重复弹窗。
- 后台通知接入现有 APNs / Web Push 通道，锁屏文案不包含私人取消原因、说明。
- 「寻找其他同行」打开新意愿编辑器，带入活动与仍有效的未来时间；时间已过则提供新的未来时间供确认。必须主动发布，旧计划不会重新激活。
- 未加入公开取消次数、信用分、押金或爽约处罚。

## 完整流程测试

执行 `scripts/qa-plan-cancellation.ts`，通过真实 HTTP API 操作三个临时账号；测试结束仅清理这三个账号。目标为 `127.0.0.1:3033` 和本地 PostgreSQL `sideseat_loop_20260926`。

| 流程 | 结果 |
| --- | --- |
| 发布意愿 → 探索推荐 → 收藏 → 打招呼 → 对方回复 → 建立聊天 | 通过 |
| 发出计划 → 对方接受 → 双方日历各有一条记录 | 通过 |
| 接收方取消已确认计划 → 双方日历移除 → 双方计划状态一致 | 通过 |
| 并发重复取消 → 只生成一条取消通知 | 通过 |
| 无关账号取消、读取/确认他人提醒 | 权限限制生效 |
| 对方读取提醒 → 确认 → 再次读取不返回该提醒 | 通过 |
| 取消后聊天记录包含原因，继续发送普通消息 | 通过 |
| 临近开始无原因取消 | 拒绝，原计划和日历保持完整 |
| 发起人撤回待回应提议；接收方不能替发起人撤回 | 通过 |

为验证结束后的反馈，测试仅把测试计划的时间移至过去，反馈和聊天仍通过鉴权 HTTP 提交。普通 V1 计划覆盖真实创建链路；带 commitment 的确认计划及改期修订使用受数据库约束的测试状态，随后通过真实取消接口验证。现有 V1 的 counter 接口仅处理待回应提议，本次没有把它扩展为新的已确认计划改期入口。

## 上线前仍需人工确认

1. **真机推送验收**：用两个签名安装的客户端验证后台、锁屏及通知权限关闭时的表现。当前已接入推送并验证应用内提醒，尚未证明 Apple 实际投递到真机。关闭系统通知时依赖下次打开应用的未读补弹。
2. **发布执行**：上线需先部署 `20260927010000_plan_cancellation_notices` 数据库迁移及后端，再发布客户端。本轮仅在本地应用迁移，没有部署生产。

体验上仍可调整的地方：多条未读取消目前逐条确认；前台补取最多有约 15 秒延迟。临近开始的 2 小时阈值为本次采用的明确规则，暂不延伸为处罚制度。
