# Preview 122：在原时间表选择最终时间，再确认邀请名单

2026-10-18，Europe/Berlin。用户要求发起人直接在时间表定最终时间，选好后复核名单并发送邀请。
产品来源 `59a289ef53fa235d88e9238d1a310664b19cb2aa`，已推送至 `codex/ios-uxui-20260922`。

## 实际流程

**大家的时间表 → 选择最终时间 → 点选开始/结束或长按拖选 → 下一步：确认邀请名单 → 发出邀请 → 每人明确确认 → 日历。**

原表在征集期间仍默认直接编辑自己的空闲。发起人主动开始选择最终时间后，表格改为编辑一个本地时段草稿，
以独立边框、日历图标及「尚未发送邀请」说明区分；人数继续显示，自己的答复和朋友的答复均不改动。
新邀请不预选整天，尚未选时段时下一步禁用；一格即 30 分钟，也能反向选择、先选开始再滚动到结束，或点日期选择当天全部配置时段。
范围限定在一个候选日期且必须连续；不同日期重新起选，不跨断点或改写旧 15 分钟边界。

名单页展示刚选的精确起止时间、时区和每个人是否全程有空，不再重复日期/开始/结束选择器。
默认名单沿用原有人员规则，发起人始终参加；其他人可勾选，未选其他人时发送禁用。
可用性提示不会自动删人或替用户决定名单。「调整时间」返回表格时保留已选时段和名单。
只有「发出邀请」调用既有邀请 API；发起人的发送表示自己确认，其他人仍需明确接受最终邀请。
取消本地选时不改变记录；另选邀请时间也使用同一张表，预填旧时段，取消时保留现有邀请和版本。

本轮仅原生交互更新，保留身份、现有答复、串行自动保存、邀请版本和 Calendar 合同。
固定时间创建及旧双人聊天计划规则保留，无网页、API、数据表、迁移或生产部署变更。

最后参与者 UI 登录明确确认，经日历搜索、详情并返回同一计划。

游客连续用例则包含首次进入计划、创建、真实空表、直接填写/分享、系统分享复制、Safari 填名直接选时、

两项测试中均不存在名单页的旧日期/开始/结束选择器。
