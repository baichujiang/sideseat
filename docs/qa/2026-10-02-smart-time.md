# 智能约时间：实施与闭环验证

日期：2026-10-02。

## 本版流程

持续聊天 → 输入框上方「智能约时间」→ 分享未来 3／7 天或下周的忙闲（从明天起，默认未来 7 天）→ 对方打开卡片 → 与自己的已同步日程求交集 → 展示 3 个共同空闲时段 → 选中后自动滚到计划表单 → 发送前刷新双方忙闲 → 对方接受 → 写入双方日历 → 继续聊天。

如果对方已在当前加载的聊天记录中分享过空闲，发起页可直接进入该分享。支持 30／60／90／120 分钟、上午／下午／晚间、换一组建议。建议优先分散到不同日期，计算时至少留出一小时准备时间。日期、建议和编辑器统一使用柏林时间。

- 新快捷入口明确隐藏日程标题、地点及分类，只分享选定日期及每日范围的忙闲。分享随范围结束过期，沿用单次使用、撤销和屏蔽规则。
- 无交集显示空状态；自己的日程加载失败显示重试，绝不按「全天有空」继续。
- 提议发送前刷新两份忙闲；选中时间不再满足共同空闲时，清除选择并提示重选。发送成功收起表单，显示等待回应，并提供返回聊天入口。
- 复用已有分享、计划、接受及日历 API，无数据库 Schema 或后端产品代码变更，无 LLM 调用，不增加模型费用；仍有原有 API／数据库请求成本。

## 已执行验证

1. **原生逻辑**：13 项通过（7 项新智能约时测试、6 项已有时间编辑测试）。覆盖共同区间、占用间隙、时长与时段、不同日期优先、提前量、重复区间去重、柏林夏令时结束、隐藏详情的请求和失效时间拒绝。
2. **原生 UI**：4 条新流程通过：分享后返回聊天、共同时间成为计划、没有共同空闲、读取失败不能伪装空闲；已有「接受计划并打开日历」及「从聊天分享卡选择并发送时间」两条回归通过（后者同步为新推荐控件与随当前日期变化的 fixture）。最后再次验证发送后表单收起及返回聊天。
3. **服务端现有逻辑**：14 项忙闲计算／详情隐藏测试通过。
4. **真实 HTTP／本地 PostgreSQL**：现有 2 条分享接口用例通过；新增完整双账号用例通过。确认分享响应无标题／地点、选中双方共同时间、PENDING 阶段没有日历记录、聊天内存在计划卡、接受后恰好生成双方两条 Calendar projection，两个账号都能通过日历接口读取同一计划。
5. **界面检查**：检查中文窄屏截图。根据截图修复选中后需自行寻找表单的问题，以及已发送后仍显示原表单的问题。三语字符串、Swift 构建、ESLint、TypeScript 检查和差异空白检查通过，具体发布结果见发布记录。

原生 UI 使用本地 fixture；接口闭环使用 `127.0.0.1:3022` 和独立的 `sideseat_ios_test` 数据库。没有向真实账号发送测试消息。唯一标记 `[smart-time-qa]` 的本地测试计划保留用于核验。所有逻辑测试无需真实个人日历。

## 实际边界与后续产品决定

- 本版适用于两人约时间；未增加多人投票、地点路程缓冲或用户独立时区偏好。
- 只依据 SideSeat 已同步的数据。未录入日程、未导入的系统日历和刷新失败的外部订阅可能缺失；不能承诺绝对无冲突。界面明确要求核对尚未记录的安排。
- 发送前读取实时数据不会锁住双方日历；发送之后仍可能出现新的安排。接受继续走现有服务端 Plan 规则，不能把候选时间当作已经占位。
- 分享沿用现有 bearer link：链接被转发后，持有人可能访问忙闲直到过期／撤销；它不是新增的「仅某接收者可读」权限模型。不会因这个快捷入口暴露标题／地点。
- 不自动访问未分享的对方日历。发起者需先分享忙闲，接收者才计算共同时间；聊天中的历史分享入口基于当前已加载的消息，过期后可回到发起页重新分享。
- 本轮未设置 Plus 门槛或使用次数。作为高频核心功能的免费基础额度／Plus 增强权益，仍需产品决定；不能将功能已实现视为收费体系已接入。
