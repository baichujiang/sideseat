# 同伴再次邀约：两项遗留问题修复方案

日期：2026-10-03。状态：已按方案实施，本地原生回归见[实施与验证报告](2026-10-03-same-peer-loop-remediation.md)；尚未发布到正式后端或手机 Preview。
依据：[第一闭环测绘报告](2026-10-03-same-peer-loop.md)。

## 设计决定

让用户在活动结束后直接“再约一次”，在聊天中清楚看到目前需要处理的邀请或下一次见面的安排。复用已结束卡片、现有计划编辑页和聊天顶部区域，保持现有五个主页面。

最短路径：**已结束活动 → 再约一次 → 选择新时间 → 发送 → 对方接受 → 双方日历**。标题、地点和参与者已有信息不要求重填，反馈不是再次联系的门槛。

## 一、活动结束后的再次邀约

### 入口与卡片

在「计划 → 已结束」和聊天里的同一张已结束计划卡片上，提供相同行为：

```text
校园咖啡                         已结束
10 月 3 日 17:00–18:00 · Campus Café
与 Mia
──────────────────────────────
你的反馈：已发生                 修改

            再约一次
```

“再约一次”采用已有自适应深色／浅色主按钮，44pt 以上点击区域。卡片信息仍打开该历史计划的聊天位置；按钮直接打开新计划编辑页，两个点击区域分开。用户无需先进入聊天再寻找输入栏旁的图标。

| 当前状态 | 呈现与行为 |
| --- | --- |
| 活动已结束，尚未反馈 | 保留原反馈问题及选项，下方提供低强调的“再约一次”；允许直接使用 |
| 自己反馈“已发生” | 将反馈收为一行可编辑状态，下方显示主按钮“再约一次” |
| 自己反馈“未发生” | 保留私密反馈，按钮文案为“重新约时间”，打开独立新计划草稿 |
| 对方尚未反馈 | 不影响入口，不暴露对方的答案或是否作答 |
| 联系已不可用 | 沿用现有联系权限与错误展示，不允许发出邀约 |

反馈和邀约相互独立：点击反馈只保存自己的答案；点击再次邀约只打开草稿；只有点击“发送邀约”才通知对方。不能把再次邀约解释为双方已经见面，也不能自动填写 Meet Again 偏好。

### 新计划编辑页

复用现有 PlanCreateSheet，标题为“再约 Mia”，底部主操作为“发送邀约”。从计划列表进入时也直接展示该编辑页；发送成功后进入原聊天并定位刚发出的计划。取消则回到原来位置，不新增消息或日历事件。

| 字段 | 初始内容 | 是否可改 |
| --- | --- | --- |
| 对象 | 原计划的另一位参与者 | 固定；与同一个人再次邀约 |
| 活动 | 原计划的标题及活动类型 | 可改，支持这次做不同的事 |
| 地点 | 原计划的地点；原来没有则为空 | 可改 |
| 日期及时间 | 未选择，显示“选择新的时间” | 必须明确选择未来时间 |
| 时长 | 手动选择开始时间后，可沿用上次有效时长作为建议 | 可改；保留现有最短时长规则 |
| 备注 | 空 | 可填；上次临时备注不自动复制 |

保留现有空闲时间选择入口。选中建议后填入时间并返回同一个草稿；只代表发起者的可用时间。只要选定有效时间，便可发送，不再添加额外“确认已选时间”的开关。未选择时发送按钮不可用，并就地提示缺失字段。

重复点击发送时沿用同一请求标识与加载状态；网络失败保留草稿和原请求标识用于现有重试逻辑。打开草稿和取消均不通知对方。

### 发送后的结果

1. 使用原聊天连接创建一个新的计划，与第一次计划分开。
2. 对方看到“你邀请了 Mia／Mia 邀请你”的普通计划卡片，可以接受、另提时间或拒绝。
3. 对方接受后，新计划加入两人日历；第一次活动及其反馈继续保留。
4. 再次邀约只表示提议见面，不代表已获得对方同意；未来计划不产生“共同经历”。

### 与既有功能的关系

代码里的 Meet Again 是“双方私下允许以后再次匹配”的机制。本方案是两位已经能聊天的人直接提出新计划，独立于 `V2_MEET_AGAIN_ENABLED`。不以开启该开关来代替新增入口。

与 `6 → 1` 的分工：此按钮用于“还是这个人”；发布新意愿继续在同行入口完成。第一版先保证这一条路径清楚，不在每张已结束卡片上再放一个同等强调的“寻找新同伴”按钮。第二闭环完成实测后再决定是否需要附加回流入口。

## 二、聊天顶部明确区分当前安排和历史来源

顶部继续保持一条紧凑摘要，主信息来自真实计划的标题、时间和状态；意愿快照只承担“相识来源”的作用。点击计划摘要定位对应的真实计划卡片，接受／拒绝仍在卡片上执行。

### 普通打开聊天时的选择规则

按以下顺序选择一个摘要；每一层都只考虑当前连接中用户有权访问的有效计划。

| 优先级 | 条件 | 顶部示例 |
| --- | --- | --- |
| 1 | 有邀请等待自己回应 | **待你回应 · 校园咖啡** / 周日 11:00–12:00 |
| 2 | 有进行中或下一次已确认活动 | **下次见面 · 校园咖啡** / 周日 11:00–12:00 · 已确认；进行中时改用“进行中” |
| 3 | 自己已发邀请，等待对方回应 | **等待 Mia 回应 · 校园咖啡** / 周日 11:00–12:00 |
| 4 | 没有以上计划，但有原始意愿 | **相识意愿 · 校园咖啡**；使用较低强调的来源摘要 |
| 5 | 没有计划或意愿来源 | 收起摘要，只显示联系人栏和聊天内容 |

同一优先级中，先显示开始时间最近的有效计划；时间相同使用固定 ID 顺序避免反复跳动。已拒绝、取消、过期及已替代的提案不占用当前安排的位置。改期提案按同一 commitment 分组：待接受的新时间与仍生效的原约定在同一组内明确展示，不能显示成两次独立见面。

有其他有效计划时，摘要旁提供低强调的“查看计划”，打开当前两人的计划列表，按“待你回应／已确认／等待对方”分组。这里复用现有计划卡片及响应入口，不再建立另一套确认按钮。摘要及列表从连接维度的计划数据获得，不能仅从当前加载的聊天消息反推。

### 历史入口保持明确

用户从已结束计划、日历事件或搜索结果打开一条特定记录时，保留该导航目标：

```text
正在查看 · 已结束
10 月 3 日的校园咖啡              查看当前安排
```

它不会在用户查看途中被最新活动替换；“查看当前安排”切回普通摘要和对应计划位置。若当前没有有效安排，则提供“返回最新消息”。从明确的意愿入口进入时，同样标成“正在查看 · 意愿”，而不是冒充当前计划。

相识意愿仍保留在历史来源卡片及聊天详情的“相识意愿”区域，点击可看原内容。只有存在已保存的来源时才展示，普通聊天不补造来源。原始活动、后续邀约和二者的状态分别保留。

### 两个修复如何连起来

```text
反馈后点击“再约一次”
  → 编辑已带入活动和地点的草稿
  → 选新时间并发送
  → 原聊天顶部：“等待 Mia 回应”
  → Mia 的聊天顶部：“待你回应”
  → Mia 接受
  → 双方顶部：“下次见面 · 已确认”
  → 双方日历出现新活动
```

旧来源不再被标成当前 Plan；点击源自第一次活动的按钮，也不会修改或改期第一次活动。

## 三、实现范围与依赖

本节保留当时约定的实现范围；实际改动和验证结果以实施报告为准。

| 位置 | 拟改动 |
| --- | --- |
| `PlansRootView`、`PlanCardView` | 增加共享的“再约一次”操作；保留反馈区域及卡片正文导航 |
| 计划编辑种子数据、`PlanCreateSheet` | 增加再次邀约模式，带入标题／类型／地点，显式要求新时间；把“需要选时间”与来源 kind 解耦 |
| `DirectChatView` | 统一接收再次邀约草稿、发送后定位新计划；从计划列表返回时带上正确连接与定位信息 |
| `ConversationContextSelection`／顶部视图 | 区分真实计划、明确导航目标、意愿来源；按上述规则选择摘要 |
| 计划查询与 store | 给摘要提供连接范围的真实有效计划及多计划列表；创建、回应、取消、改期和前台恢复后刷新 |
| 中文／英文／德文本地化 | 增加再约文案、等待状态、相识意愿、历史查看状态；保持实际对方名称 |

**数据边界：** `NativePlanDraft` 目前要求一个 origin，而且 `needsTimeSelection` 绑定 MUTUAL_OPPORTUNITY。应将普通预填数据与受信任来源引用分开，或使预填 origin 可选并增加明确的时间选择策略。再次邀约通过现有连接的新建计划能力提交，`origin` 省略，`counterOf` 为空；不能伪造 REPEAT 来源，也不能复用第一次已经消费过的 mutual origin。

**查询依赖：** 当前 `GET /api/v1/plans` 为用户级查询，上限 100 条，结束历史只返回近 14 天；直接在其结果中筛选对方不能保证摘要完整。建议扩展现有读接口：先在服务端按已授权 connection 筛选并处理状态／当前 revision，再返回摘要所需有效计划和可分页的列表。详情及明确历史目标仍使用单条计划读取能力。返回完整性需明确，不能把加载失败或截断当成“没有计划”。此修改预期不需要数据库结构迁移或新的写入生命周期；具体接口以实施时契约核验为准。

**刷新：** 本人操作成功立即同步本地摘要；对方变更复用现有聊天更新触发计划刷新；进入聊天和从后台恢复重新读取。加载时保留已知摘要，失败提供轻量重试，不自动退回旧意愿并称其为当前计划。

## 四、交付顺序和验收

先实现“再约一次”入口及正确草稿，接着替换顶部摘要选择和来源文案，最后在同一次 Preview 候选上重跑第一闭环。两处一起验收，避免只增加入口但仍显示错误上下文。

验收要点：

1. 已结束页和聊天卡片都能一次点击进入带入原活动的再约草稿；未反馈者也能使用。
2. 时间最初未选择；取消不产生任何新数据；明确选择后才能发送。
3. 第二次计划使用同一 connection、独立计划 ID、无旧 origin 或 counterOf；原计划及反馈保持不变。
4. 接受前没有新日历事件；接受后双方各有一条对应新计划的事件。
5. 对方未反馈不阻断再次邀约，也不泄露对方的私密反馈；Meet Again 开关关闭时直接邀约仍可用。
6. 双方分别看到“等待对方／待你回应”，接受后变为“下次见面”；顶部点击到正确计划。
7. 同一聊天有多计划、旧消息被分页未加载时，摘要仍正确；改期提案与原约定保持关联。
8. 从历史计划进入仍定位历史记录，且明确显示“正在查看”；可返回当前安排。
9. 原生小屏、中文／英文／德文、深色及最大字号下状态和按钮可读；VoiceOver 区分卡片正文、再约按钮和查看计划。

交付证据沿用原报告的截图、独立数据库断言和两账号原生 UI 测试，另补摘要选择的模型测试与连接查询的授权／完整性测试。两台实体设备通知及正式环境时延在部署后的验收中单独确认，不能用本地结果代替。
