# Unlimited invitation capacity — in progress, not deployed

Production remains `dpl_HAeYXJf2hvaWiA2RcyBb3vfPKbcC` and retains the 20-person cap. Do not promote this work until compatibility with already installed iOS clients and the physical-device release path have been resolved. The existing iOS client treats `FIXED` with `expectedCount: null` as a two-person target, so a backend-only rollout would incorrectly make an unlimited invitation look full. The default iPhone 14 Plus was unavailable during this work; no native build was installed, and no App Store or TestFlight distribution was authorized.

The local implementation uses an explicitly null `linkParticipantCount` for an open link without a user-defined cap, an integer for an open link with a cap, and an omitted property for the existing closed-roster contract. It removes the 20-person roster validation, retains explicitly saved historical limits, and batches web contact sharing into requests of at most 19 contacts while reporting partial failures. Shared web and updated iOS presentation handle a null target. Existing data needs no schema migration. Existing iOS builds remain incompatible until an appropriate compatibility/rollout solution is established.

Local checks: the browser created an unlimited invitation and a 35-person limited invitation, both confirmed by API readback. A plan was confirmed and published with 25 participants; a 26th guest then joined through the shared page. A separate capped plan rejected an additional guest. Twenty own contacts received a plan via the web batch flow, and re-sending reported no duplicates. Twenty-one own accounts confirmed a plan, the owner published it, and each of the 21 schedules contained one event with the other 20 participants. Focused ESLint, eight domain tests, and the API regression test passed. An iOS Simulator build passed; 37 time-poll tests passed before the final removal of native sender caps, and the final source compiled again. No physical iPhone or production behavior was tested.

Twenty-three own local test accounts and five owned plan links were cleaned; the regression test cleaned its own account. One initial test account needed a test-only credential reset before API deletion after the test omitted an idempotency key; its exact owned identity was checked and the old cookie returned 401. Existing workspace changes to `next-env.d.ts` and `tsconfig.json` were left untouched. Full local TypeScript checking encountered existing Next route-type errors, and the OpenAPI contract check reported two existing undocumented routes (`mutual-opportunities/{opportunityId}/safety` and `time-polls/{token}/guest-recovery`); neither check is claimed as passing.
