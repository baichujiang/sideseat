# Preview 134 — Plans home first implementation

2026-10-19, Europe/Berlin. The owner-approved photographic first-version concept is the implementation baseline. The current release adds activity identity and real friend context, preserving the existing manual and conversation-bound planning flows.

## Scope

- First use: photo collage, a concrete purpose statement, one create action, shared-link entry and a directly visible optional example sheet.
- Existing plans: compact activity thumbnails/default themes, real organizer/inviter names and existing avatar previews, viewer-specific status and actions. Needs-you remains vertical; waiting remains horizontal with next-card peek and View all. Accessibility text reflows vertically.
- Default covers are decorative and derived from the existing title. They never change the activity or require an upload. Undecided activities keep a neutral suggestion theme.
- One overview tap opens the existing detail; it never sends or accepts. Availability, explicit invitation versions/rosters, individual acceptance, Calendar, cancellation and expiry retain existing contracts.
- Additive read-only list fields: organizer and up to three existing visible people, excluding the viewer and organizer. Invitation phases preview selected invitees, including guests and fixed-time participants without availability responses. Blocked account previews are filtered. Old clients/records remain supported.
- This release implements the approved home screen. Share-page appearance and timetable interaction retain Preview 133; their real flows were rechecked against the API update. No database migration or new permission.

## Observed issues and repair

The first UI run passed 12/13 cases. The new example case found that expanding the example below the home content did not bring it into view; the entry now opens an immediately visible read-only sheet. Final full 13-case UI rerun passed. One earlier runner invocation executed no tests because moving xctestrun changed TESTROOT resolution; absolute product paths corrected it. The first final build attempt waited on a busy test destination; the subsequent signed build/install completed after UI teardown.

The first release-preparation command used the release directory as its input and stopped before copying the overlay. Its unused staged deployment was canceled; public aliases never moved to it. A second intermediate candidate was canceled before promotion when fixed-time companion metadata was completed. Only the final, source-verified candidate was tested and promoted. An unused automatic Git preview finished before cancellation could apply; it was never promoted.

The initial health probe included a nonexistent /api/v1/config route (404), which is not an application regression. The final health record uses seven existing routes, all HTTP 200. UI fixture screenshots deliberately use an unavailable localhost API for isolation, so their network banner is not a production health result; real-account screenshots and API checks are separate evidence.
