# Preview 145：发起人随时正式发出

结论：受邀者可以接受、拒绝或暂不回复。发起人不再等全部回应或人数凑齐，主动「正式发出」后，只给已接受者同步日历和成行通知。所有人接受也不会自动发出。正式发出后，仍可在开始前接受；改为拒绝会移除本人的日历并更新同行者。

## 已通过

- 75 项原生单元（42 项计划/时间表，11 项通知，22 项导航），13 项计划领域和 32 项发布/推送协议检查。导航单元实际观察新通知触发 Plans 与 Calendar 各一次刷新，并验证对应计划路径。
- 最终候选与正式各 12 组 Chromium/WebKit 完整检查：四账号和游客，接受/拒绝/忽略并存时发出、只有发起人时发出、全员接受仍等发起人、发出后加入/退出、唯一日历、版本/权限/容量和取消回收。此前同一功能候选/正式各 12 组、原有活动建议到日历 22 组也通过。
- 默认 iPhone 14 Plus 真机直接邀请 **111.895 秒 / 8 API 阶段**：只有发起人时正式发出，朋友随后从链接进入并接受，日历往返。
- 真机 App 双账号完整流程 **353.253 秒 / 13 API 阶段**：创建、分享、直接编辑、手动提交、重进恢复、最终选时、名单调整/取消、只读高亮、深色最大字号、接受后仍 INVITING、发起人正式发出、双方唯一日历及返回计划。
- 最终客户端 App → 手机 Safari **199.113 秒 / 9 API 阶段**：首次进入、创建、分享、游客填写、最终邀请、接受后不自动确定、发起人主动发出、日历往返。截图断言顶部为「待你正式发出」。
- 两种真实推送顺序各得到 Apple APNs HTTP 200，共 **2 条**；重复发送/重复接受没有增加通知。提供方接收已验，系统通知横幅未单独录像。游客通过原分享页查看，没有账号日历或设备推送通道。

## 修复与复验

首轮完整原生在最大辅助字号下，新增的第三个固定底部动作遮挡了受邀时间格。「暂不回复」移到滚动内容后，最大字号与整条原生链路重跑通过。

下一轮已通过大字号、接受和正式发出，但测试脚本使用了不存在的 `plans-section-upcoming`；按实际层级改为 `plans-tab-upcoming`，再用新账号从头重跑至日历返回通过。初始失败、阶段记录和回收凭据保留，不计作通过。

运行日志实际发现 Preview 令牌被发送到普通版主题，Apple 返回 `DeviceTokenNotForTopic`。仅在已知普通版主题 + sandbox + 此明确错误时，改用已知 Preview 主题；普通版 production 路径不变。协议测试和两条真实接收回执通过。前台的新通知类型也补齐计划/日历刷新。

QA runner 编译变量冲突、旧入口标识、开发服务连接超时及测试启动参数问题均在证据中记录。恢复 Mac CoreDeviceService 后继续使用同一默认手机，没有重启手机或换设备。
