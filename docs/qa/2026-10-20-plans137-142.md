# 计划手动提交：五项按序验收与 Preview 142 收尾

五项依次实现，每项通过对应单元、真实网页/API 和默认 iPhone 真机检查后，再开始下一项；各阶段独立提交、推送并安装 Preview 137–141。最终复核补上读取重试不提交草稿的回归，形成 Preview 142。

## 实际行为

1. 时间格只更新本机草稿；「提交我的空闲 / 保存修改」才发送完整答复。昵称失焦、离开、后台和其他计划操作不提交空闲。
2. 未提交、提交中、已提交、失败分开显示，底栏显示所选天数和时长。热图、人数及名单只统计已提交答复；空答复仍算已填写。
3. 有草稿时继续更新朋友答复和计划阶段，自己的选择与昵称不会被刷新覆盖；最终邀请到达后直接显示高亮时间表并可确认。
4. 草稿不禁用最终选时、名单复核或发邀请，发送不提交或清空草稿。实际请求进行中仍阻止冲突或重复动作。
5. App 按账号和计划、网页按填写人和计划恢复本地草稿，明确标为未提交。失败和慢响应期间的新修改保留，只清除已得到确认的对应快照。

原 API、已有记录、活动选择、名单/人数、邀请版本、到期、逐人明确确认和日历规则保留。没有数据库结构、迁移或依赖变化。

## 发现并修正的事项

- 第一项网页脚本的「这些时间我都没空」定位缺字；修正后全新账号双浏览器重跑通过。
- 第二项修正继续编辑时过时的提交失败状态，最终包重新构建、单元和真机复验通过。
- 第三项补上迟到读取失败的时序保护，最终网页重跑 22 项通过。清理脚本改为先读详情中的 invitationVersion，再取消和删除，404/401 清理通过。
- 第四项首轮 UI 通过但未同时启动 Mac 观察器；保留首轮结果，清理后重新用新账号同步跑 UI 和 4 个 API 边界，最终通过。
- 第五项测试 fixture 的复杂字典导致 Swift 编译超时；拆分表达式后最终 22 项原生通过。另保留并验证「提交中改回旧服务器值」的新草稿，防止旧确认清除它。
- 候选首轮跨计划检查在身份切换请求完成前导航，导致仍按上一身份恢复。脚本改为等待表单关闭和当前填写人确认；新账号候选 34 项、正式 34 项全部通过，首轮数据清理证据保留。网页产品代码未因此修改或重建。
- 收尾复核发现 App 的读取失败「重试」仍共用提交入口。142 按失败种类分开：读取失败只重读，提交失败才提交；新增回归验证草稿保留且 0 次保存，并以 23 项原生及最终两条完整真机复验。
