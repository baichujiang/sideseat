## 5. iOS 工程与架构

建立 `ios-native/SideSeat.xcodeproj`。工程必须可从干净检出状态通过记录在案的命令构建，不依赖个人机器上的未提交配置。若使用 XcodeGen 或其他工程生成工具，必须固定版本、提交声明文件并在 CI 中自动生成；若直接维护 `.xcodeproj`，必须避免无意义的 `project.pbxproj` 顺序抖动。

在阶段 2 开始时，根据仓库与 CI 条件明确选择并记录一种工程管理方式，不同时维护两套互相漂移的工程来源。所有 Target、Scheme、Build Configuration、Entitlement 和测试计划必须提交并能从干净检出复现。

应用根结构：

- `TabView`：Home、Discover、Chats、Me。
- 中间“+”是创建动作而非内容 Tab；点击后使用原生 Sheet 选择创建 buddy post 或 activity。
- 每个 Tab 拥有独立 `NavigationStack`、类型安全 Route 和独立导航历史。
- Deep Link、Push 和登录后恢复导航由统一 `DeepLinkRouter` 处理。
- Sheet、Alert 和全屏页面使用枚举状态，避免多个互斥 Boolean。

全局依赖建议包括：

- `AppContainer`
- `SessionStore`
- `APIClient`
- `RealtimeClient`
- `PushManager`
- `DeepLinkRouter`
- `CacheStore`
- `MediaUploader`
- `LocationProvider`
- `ModerationClient`
- `StoreKitManager`
- `AppEnvironment`

使用 `@Observable`、`@State`、`@Environment` 和 Swift Concurrency。共享服务通过环境注入，功能局部依赖优先使用初始化参数。不得建立承载整个 App 的巨型 ViewModel，不得在 View `body` 中发起网络请求。异步操作必须处理 loading、empty、error、retry、取消和页面生命周期。

状态所有权遵循最窄原则：单页面 UI 状态使用 `@State`，子视图可变值使用 `@Binding`，根级共享引用状态使用 `@Observable` 并由根视图持有，跨功能服务使用 `@Environment`，功能局部服务使用初始化注入。Sheet 优先使用基于枚举或模型的 `.sheet(item:)`；导航使用可编码、可测试的类型安全 Route。

按 Auth、Home、Calendar、Courses、Discover、Activities、Profiles、Inbox、DirectChat、CourseChat、GroupChat、Plans、ScheduleShare、Feedback、Settings 划分功能。领域模型、DTO 和状态机不得依赖 SwiftUI。

使用 Development、Staging、Production 三套 `.xcconfig`。配置文件只保存非秘密地址和开关；Token、Key 和证书不得进入仓库。Production 必须在构建期或启动期明确拒绝 `localhost`、明文 HTTP API 和测试专用开关，且该保护需要自动化测试。

## 6. API v1、OpenAPI 与兼容迁移

原生客户端不得依赖 HTML、RSC Props、页面刷新机制或 Prisma 原始返回值。

- 新增 `/api/v1`，旧 Web 路由继续兼容。
- 将页面中的 Prisma 查询和业务规则逐步提取为共享服务，由 Web 与 API v1 共同调用。
- 使用稳定 DTO，不直接暴露 Prisma Model、内部字段或数据库枚举细节。
- 成功响应：`{ data, meta? }`。
- 失败响应：`{ error: { code, message, field?, retryable, requestId? } }`。
- 未登录 API 必须返回 JSON 401，不得重定向 HTML。
- 时间统一传输 ISO 8601 UTC；重复规则、用户时区和本地显示语义必须明确。
- 列表使用稳定游标分页；聊天使用消息 ID/时间游标补拉，保证无重复、无漏项。
- 可重试写操作支持 `Idempotency-Key`，服务端存储幂等结果并限定有效期。
- 请求携带平台、App 版本、构建号和关联请求 ID；服务端为每个响应返回可追踪的 request ID，并支持最低兼容版本和强制升级响应。
- OpenAPI 是原生客户端契约的唯一来源。选择并固定一种兼容当前 Swift 工具链的生成方案；生成目录只由脚本写入，文件头标记 generated，禁止手工修改。CI 必须重新生成并以 clean diff 验证规范、实现和 Swift DTO/Client 没有漂移。
- 所有破坏性契约变化必须新建字段、版本或迁移窗口；不得在已发布 App 仍可能调用时直接删除字段、改变枚举语义或复用错误码。

至少补齐：当前用户、公开资料、完整 Inbox、联系人、私聊/课程聊天/群聊历史、Feed、帖子详情、我的帖子、我的活动、收藏课程、计划、拉黑列表和通知状态。

数据库变更采用 expand-migrate-contract：先添加兼容字段或表，再迁移数据和调用方，最后才清理旧结构。每个 Migration 必须在独立测试数据库验证全新部署与已有数据升级，并记录回滚或前向修复方案。禁止直接对生产数据库试错。

## 7. 认证与安全

- 原生登录返回短期 Access Token 和可轮换的 opaque Refresh Token。
- Refresh Token 只存 Keychain；服务端只保存哈希、设备会话、创建时间、最后使用时间和撤销状态。
- 每次刷新轮换 Refresh Token；重复使用旧 Token 时撤销对应 Token Family，并要求重新登录。
- 支持退出当前设备、撤销其他设备和账户安全页查看设备会话。
- Web 继续使用 HttpOnly Cookie，不破坏现有登录。
- 登录、注册和找回能力必须先核对当前后端。用户名/邮箱/手机号、OTP 等未存在能力属于明确的上线新增项，不得用假接口或本地状态代替。
- 如果 App 引入第三方或社交登录作为主要账号登录方式，必须重新核对并满足当时有效的 Sign in with Apple 等价登录要求；若只使用 SideSeat 自有账号系统，则在证据账本说明不适用依据。
- 支持 username 修改冷却期、密码修改、登录邮箱修改、退出和完整账户删除。
- 对登录、OTP、注册、发帖、开新会话、消息、上传、举报和公开分享实施服务端速率限制。
- 上传校验真实 MIME、扩展名、大小、像素尺寸和解码结果；客户端压缩图片并移除非必要 EXIF。
- 日志和监控不得记录密码、Access/Refresh Token、完整私聊正文或原始敏感图片。
- 明确认证并发语义：多个请求同时收到 401 时只允许一次 Refresh，其余请求等待同一结果；刷新失败或检测到 Token 重用时原子清理会话、缓存和受保护导航状态。

## 9. 实时消息、APNs 与 Deep Links

- 前台使用 `URLSession` 消费 SSE，服务端返回带稳定事件类型、版本、事件 ID、会话 ID、资源 ID 和服务器时间的结构化事件，不依赖刷新网页。
- 服务端支持心跳、`Last-Event-ID` 或等价游标恢复；客户端把 SSE 视为“有变化”的信号，以受权限保护的历史接口补拉真实数据，不把单次连接当作唯一消息来源。
- 实现断线重连、带抖动的指数退避、游标补拉、重复事件去重、乱序保护、网络恢复和前后台切换；401 只触发一次受控刷新，不得形成重连风暴。
- App 进入后台后停止持续 SSE，不使用后台轮询维持聊天。
- 后台和终止状态由 APNs 唤醒用户；完成 APNs HTTP/2 Token 认证、发送、失效 Token 清理和多设备支持。
- 每次启动更新 Device Token，退出时解绑当前设备；Sandbox 与 Production Token、Bundle Environment 和失效原因必须隔离。载荷仅含最少路由信息，不含敏感消息正文。
- 点击通知能够安全导航到聊天、活动、计划或日程。

配置 Associated Domains 和无重定向的 `/.well-known/apple-app-site-association`，支持用户资料、帖子、活动、课程、聊天、共享日程和计划请求。所有 URL 参数必须校验；未登录时保存安全目标并在登录后恢复；删除、付款、接受请求等写操作不得由深链直接执行。

## 10. UGC、隐私与 App Store 合规

SideSeat 是社交和用户生成内容应用，上线前必须具备：

- 发布前过滤不当公共内容、举报入口、及时处理机制、拉黑能力和公开支持联系方式。
- 服务端 `ContentModerationService` 抽象；首发可接 OpenAI 文本与图片审核，Key 仅存在服务端。

- 稳定审核错误码、人工复核队列、管理员封禁及审计记录。
- App 内可发起完整账户删除，不得只提供停用；关联用户内容按法律与产品政策删除或匿名化，并向用户说明必须保留的数据。
- 建立数据盘点与保留矩阵，覆盖账号、学校资料、位置、图片、聊天、举报证据、推送 Token、日志、分析和交易记录；每类数据记录用途、保存位置、第三方处理方、保留期限、删除方式和访问权限。
- 提供 `PrivacyInfo.xcprivacy`，准确声明数据收集和 Required Reason API；生成并检查 Xcode Privacy Report。
- 权限文案按需申请并说明用途。拒绝相机、照片、位置、通知后仍可使用不依赖该权限的功能。
- App Store Privacy Nutrition Labels、隐私政策和实际代码/第三方 SDK 行为保持一致。
- 发布候选版本必须重新核对当时有效的 Apple App Review Guidelines、Human Interface Guidelines、隐私清单和上传工具链要求；将核对日期、规则版本或页面链接写入证据账本，不得仅依赖本文中的静态描述。

## 11. StoreKit 2

iOS 中“支持 SideSeat”使用固定档位消耗型 In-App Purchase；Web 保留 Stripe。

- iOS 内不跳转 Stripe，不提供任意金额输入。
- App Store Connect 与本地 StoreKit Configuration 使用相同 Product ID。
- 处理 verified、unverified、pending、userCancelled 和失败。
- 将验证通过的 JWS 发送服务端验证，并按 Transaction ID 幂等记录。
- 服务端验证环境、Bundle ID、Product ID、Transaction ID 与签名并完成幂等持久化后，才可结束交易；网络或服务端失败时保留未完成交易并安全重试。必须在架构文档中为同一交易明确且只选择一种结束路径：由 App 调用 StoreKit `Transaction.finish()`，或由服务端调用 App Store Server API 的 Finish Transaction endpoint。不得两端重复结束，也不得在持久化和交付流程完成前结束。
- App 启动时监听 `Transaction.updates` 并处理 unfinished transactions。
- 消耗型支持款不展示误导性的“恢复购买权益”；服务端记录仅用于交易审计与幂等，不表示永久权益。
- 覆盖成功、取消、pending、重复回调、断网、服务端失败和 App 重启恢复处理。

## 12. 缓存、错误与可观测性

- 默认使用 SwiftData 缓存 Home、Courses、Discover、Inbox 和 Me 的最近成功只读数据，并设置 Schema 版本、迁移、容量和失效策略。若仓库事实证明其他持久化方式更合适，必须先记录性能、迁移、测试和隐私方面的决策依据，不得同时维护两套互相漂移的缓存来源。
- 缓存按用户隔离；退出、账户删除或切换账号时清除敏感缓存。
- 离线时展示缓存和明确状态；写操作不得显示假成功。
- 写操作具有 loading、success、error、retry；Optimistic UI 失败必须回滚。
- Token 过期、401 刷新、超时、取消、429、5xx、图片失败、SSE 中断和数据库不可用都要映射为稳定、可理解的表现。
- 使用 `OSLog` 分类日志并对敏感字段执行 privacy 标记；接入崩溃和关键网络错误监控，上传 dSYM，但不上传完整消息正文或 Token。
- 为请求传播 request ID，便于客户端错误、Vercel 日志和数据库操作关联排查。
- 监控必须区分 Development、Staging 和 Production，提供采样、脱敏、保留期限与删除策略；第三方 SDK 上线前检查许可证、隐私清单、数据出口和关闭采集的方法。

发布候选版本至少重新核对以下 Apple 官方来源，并在证据账本记录核对日期与结论：

- App Review Guidelines：`https://developer.apple.com/app-store/review/guidelines/`
- Account deletion：`https://developer.apple.com/support/offering-account-deletion-in-your-app/`
- Privacy manifests：`https://developer.apple.com/documentation/bundleresources/privacy-manifest-files`
- App privacy：`https://developer.apple.com/help/app-store-connect/manage-app-information/manage-app-privacy`
- StoreKit 与 App Store Server API：`https://developer.apple.com/storekit/`、`https://developer.apple.com/documentation/appstoreserverapi`
- Upcoming SDK/Xcode requirements：`https://developer.apple.com/news/upcoming-requirements/`

若官方要求与本文冲突，以发布时有效的 Apple 官方要求为准，并将差异作为带日期的决策记录，而不是静默修改实现。

外部阻塞必须集中列出：事项、所需账号/密钥、负责人、验证方法和解锁后命令。典型事项包括 Apple Team/签名证书、APNs Key、Associated Domains、App Store Connect IAP 商品、TestFlight 外部审核、生产监控 DSN、生产审核密钥、真实账号和真机验收。外部阻塞存在时，应完成 Mock、Sandbox、编译和不依赖该凭证的测试，并明确区分“代码就绪”“提交就绪”“已提交审核”和“Apple 已批准”。AI 不得保证或虚构 Apple 的审核结果。

## 16. 实施阶段与退出条件

1. **阶段 0：审计与基线**。完成仓库审计、基线测试、迁移主文档、需求追踪矩阵及功能/API/数据矩阵。退出条件：所有现有用户入口有归属，未知项和风险有稳定 ID，测试与数据库环境被明确隔离。
2. **阶段 1：共享契约与认证基础**。完成 API v1 基础规范、OpenAPI 生成链路、原生认证、错误模型、测试数据库、必要的兼容 Migration 和基础 CI；各业务域的 v1 接口在对应纵向阶段继续补齐。退出条件：认证轮换、并发 401、幂等基础设施、权限、速率限制和 OpenAPI 漂移测试通过，旧 Web 登录与关键 API 回归通过。
3. **阶段 2：原生基础设施**。完成原生工程、设计系统、导航、Session、环境、缓存、本地化和 Deep Link 基础设施；具体业务深链在对应功能阶段实现。退出条件：干净检出可构建，Development/Production 配置隔离，四个 Tab、登录恢复、错误/离线入口和类型安全导航可自动测试。
4. **阶段 3：Home、Calendar、Courses**。形成首个可用纵向版本。退出条件：真实账号可读取和修改日历、浏览课程并完成核心课程动作；时区、重复日程、空/错/离线状态和对应 Web 回归通过。
5. **阶段 4：Discover、Activities、Profiles**。退出条件：真实 API 支撑浏览、搜索、创建、编辑和关键关系动作，图片上传、隐私、拉黑和内容可见性规则经过集成与 UI 测试。
6. **阶段 5：Inbox 与聊天**。完成 Direct Chat、Course Chat、Group Chat 和双账号实时闭环。退出条件：历史补拉、实时到达、未读、重连、图片、位置、搜索、举报、拉黑和前后台恢复通过；真机专属项明确进入人工验收清单。
7. **阶段 6：Plans、Schedule Share、Feedback、Settings、账户删除与 StoreKit**。退出条件：所有服务端状态机、共享可见性、完整删除流程及 StoreKit Sandbox 场景通过，失败和恢复路径无假成功。
8. **阶段 7：发布收敛**。完成 APNs、内容审核、无障碍、性能、隐私、监控和 App Store 发布验收。退出条件：无未关闭 P0/P1，Release Archive/Validate、隐私报告、发布资产、模拟器矩阵和可执行的真机/TestFlight 清单均有证据。

每阶段结束必须更新主文档、运行对应测试、记录失败与修复结果，并在用户已授权提交时创建范围清晰、可审查的 Commit。提交前必须检查 staged diff，只包含本阶段由当前执行者负责的文件，不得混入用户已有修改。只有当前阶段闸门通过后才进入下一阶段。TestFlight 上传依赖外部账号时，先完成能够在当前环境执行的 Archive/Validate 和外部阻塞说明，不得因此暂停后续不依赖账号的实现。

阶段内部按纵向切片推进。例如聊天切片应同时包含所需 API、DTO、Swift 状态、UI、错误处理和测试，而不是先批量创建所有空 Screen。允许为了共享契约兼容而提前完成下一阶段的少量基础工作，但必须在主文档说明原因，不得借此跳过当前阶段闸门。

每个纵向切片开始前先写清：稳定需求 ID、用户可观察行为、涉及的现有 Web 规则、API/数据影响、测试方式和回滚边界。切片结束时逐项对照，不以文件数量、代码行数或编译通过代替行为完成。

## 17. 最终完成定义与结论用语

只有同时满足以下条件才能宣布任务完成：

- 功能矩阵中全部普通用户功能达到“已实现、自动测试通过、人工验收通过”。
- Web、PWA、旧 API 和现有数据库继续工作。
- TypeScript、API、Swift、XCUITest 和 Web E2E 全部通过，并保存实际结果。
- Release Archive 不含测试账号、秘密、`localhost`、未实现入口或调试后门。
- 两个真机账号完成登录、日历、发现、聊天、计划、共享、推送、支持付款和账户删除闭环。
- Universal Links、APNs、StoreKit、权限拒绝、弱网、离线、后台和冷启动经过验证。
- 数据库 Migration 在测试和 Staging 环境验证通过，并有回滚或前向修复记录。
- Privacy Manifest、Privacy Report、隐私政策、UGC 机制和 App Store Privacy 回答一致。
- TestFlight 回归通过，App Store 隐私、权限、年龄分级、测试账号、审核说明、支持 URL 和 IAP 审核信息齐备。
- 最终报告列出修改文件、API、Migration、测试命令、实际结果、性能证据、已知风险和账号持有人仍需完成的外部配置。

如果 Apple 账号、签名、生产密钥、TestFlight、真机或人工审核条件不在当前执行环境中，则不得宣布“任务完成”；此时可达到的最高状态是“代码就绪，等待外部验收”或“提交就绪”。外部条件后来补齐后，必须从对应证据点继续验证，而不是沿用旧结论。

不得把“代码已写但未测试”“仅模拟器通过”“等待生产凭证”“以后补齐”或“接口暂时返回假数据”描述为已上线。若仍有外部阻塞，最终状态必须是“代码就绪，等待列明的外部验收”，而不是“已完成上线”。

最终只能使用以下结论之一，并给出对应证据：

- **工程实现中**：仍有可由当前环境继续完成的代码、自动化测试、修复或文档工作。此状态下不得停止，除非用户明确暂停。
- **代码就绪，等待外部验收**：当前环境内所有可执行工作与自动化闸门已完成，剩余项仅为已精确列明的账号、签名、生产配置、真机或人工验收。
- **提交就绪**：Release Archive/Validate、生产配置核对、TestFlight 回归和 App Store 资料均已完成，但尚未声称 Apple 已批准。
- **已发布**：只有 App Store Connect 的真实状态和公开版本能够验证时才能使用；AI 不得预测审核通过时间或保证审核结果。

## 18. 每次阶段汇报格式

每次汇报仅包含高信号信息，并以整体任务状态开头：

1. 整体状态：工程实现中 / 代码就绪，等待外部验收 / 提交就绪 / 已发布。
2. 本次完成的用户可观察行为、稳定需求 ID 和对应文件。
3. 实际运行的命令、退出码、通过/失败/跳过数量和关键产物路径。
4. 新发现的风险、兼容性影响和处理方式。
5. 主文档中更新的状态及证据位置。
6. 下一步正在执行的唯一纵向切片和第一条命令。
7. 仅在确实需要账号持有人操作时列出外部阻塞、负责人、精确操作和解锁后的验证命令。

现在开始执行：

- 若主文档不存在，从阶段 0 开始，先读取真实仓库、保护现有未提交修改、建立迁移主文档和证据账本。
- 若主文档已经存在，先校验其中证据与当前仓库是否一致，然后从唯一标记为“开发中”的任务继续，不得重置计划或重复从阶段 0 开始。
- 持续实现、运行和修复，直到完整上线前测试通过，或只剩已经精确记录的外部阻塞。

不要只返回计划。先简要说明正在检查什么，然后实际操作仓库并产出可验证结果；除非用户另行授权，这里的“产出”不包含 Git Commit、Push、TestFlight 上传或 App Store 提交。
