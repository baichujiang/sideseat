## 2. Current Architecture

### Web and backend

- Next.js 15.5.20 App Router, React 19.2.5, TypeScript 5.9 and Prisma 5.22 with PostgreSQL and Vercel.
- Server Components frequently query Prisma directly. Twenty-four user/admin `page.tsx` files contain direct Prisma calls, including Courses, Discover, Profile and several Inbox views.
- A smaller set of reusable query/load services already exists under `lib/queries`, `lib/home`, `lib/discover`, `lib/calendar` and `lib/inbox`.
- `lib/home/load-home-schedule-payload.ts` is already shared by Home RSC and `GET /api/home/schedule`; it is the strongest current extraction pattern.
- Existing JSON helpers return `{ success: true, data }` and `{ success: false, error, code? }`. This is not the target v1 contract.
- `requireUser()` redirects to `/login`, so it must not be used by native JSON endpoints. API v1 needs a JSON-only authentication guard.
- `npm run build` runs `prisma migrate deploy` before `next build`. Build verification must always inject an explicitly approved local/test database.

### Authentication

- Access token: HS256 JWT, subject is user ID, short lived, signed by `ACCESS_TOKEN_SECRET` or `SESSION_SECRET`.
- Web refresh token: random opaque token stored as SHA-256 in `Session` and as an HttpOnly cookie.
- Current `Session` contains only `id`, `userId`, `tokenHash`, `expiresAt`, `createdAt`.
- Current `/api/auth/refresh` reads only the browser cookie and does not rotate the refresh token.
- `getSessionUser()` supports either the refresh cookie or a Bearer access token, so existing routes can authenticate access tokens when they avoid redirecting guards.
- Login lookup supports the identifiers implemented by `findUserForLogin`; schema already has unique username, optional unique email and optional unique E.164 phone.
- Username and nickname are separate. Username is unique and has `usernameUpdatedAt`; nickname is display-only and non-unique.

### Realtime and notifications

- Direct, course and group chat expose `messages/stream`, `messages/latest` and message mutation routes.
- Current Web clients use SSE as a latest-ID notification and refresh/query the database-backed page state.
- Native clients require structured events or a cursor plus complete history APIs; they cannot use `router.refresh()`.
- `NativePushDevice` and `/api/push/native-register` persist device tokens.
- No verified server APNs HTTP/2 sender, delivery retry, invalid-token cleanup or notification routing service exists at baseline.

### Payment, moderation and links

- Web support payments use Stripe at `/api/tip/checkout`.
- No StoreKit 2 product, server transaction verification or transaction ledger exists at baseline.
- Reports, blocks, moderation blocks and admin review pages exist.
- No provider-backed pre-publication text/image moderation service exists at baseline.
- No checked-in `apple-app-site-association`, Associated Domains native entitlement or centralized native deep-link router exists at baseline.

## 3. User Journey Inventory

### Authentication and onboarding

1. Anonymous or guest user can browse permitted surfaces.
2. User signs up through email OTP, phone OTP or the implemented credential path.
3. User logs in using a supported identifier and password.
4. New account completes onboarding and profile basics.
5. User can reset password, change password, login email and username subject to existing rules.
6. User can end a guest session, log out, revoke sessions where supported and delete the account.

### Main navigation

- Home: schedule and calendar.
- Discover: Find buddies and Activities.
- Center create action: choose buddy post or activity; it is not a fifth content tab.
- Chats: merged direct, course and group inbox.
- Me: profile summary, personal content and settings.

### Core collaboration journey

1. Discover a buddy post, activity, course or user.
2. Open a connection or join the relevant social/course context.
3. Exchange direct, course or group messages.
4. Share availability or a schedule link.
5. Propose, counter, accept or decline a plan.
6. Accepted plan is written to the appropriate calendars.
7. Notification and unread state lead each participant back to the correct context.

## 7. Native Architecture Decisions

- New project lives in `ios-native/`; existing `ios/` remains untouched until native acceptance.
- Root `TabView` has Home, Discover, Chats and Me. Center create action is presented separately.
- Each tab owns an independent `NavigationStack` and typed route path.
- Shared dependencies are assembled by `AppContainer`; feature state remains local and uses Observation.
- DTO/domain targets do not import SwiftUI.
- Network layer performs one coalesced token refresh for concurrent 401 responses and retries each safe request at most once.
- Deep links are parsed centrally into validated route enums. A link never executes a destructive write.
- SwiftData stores only versioned, user-isolated read caches. Sign-out and account deletion purge protected cache data.
- Development, Staging and Production use `.xcconfig`; secrets never live in the project.
- SPM dependencies are added only for demonstrated needs and must include license/privacy review.
- `openapi/v1.json` is the native contract source. Apple Swift OpenAPI Generator 1.13.0 produces committed Types/Client files against Swift OpenAPI Runtime 1.12.0; both generation outputs and the Xcode project are deterministic and checked for clean diffs in CI.

## 8. Compatibility and Migration Strategy

1. Add `/api/v1` without changing existing endpoint shapes.
2. Extract shared query/services from RSC pages one domain at a time.
3. Add schema fields/tables with backward-compatible defaults or nullable columns.
4. Deploy server/schema support before shipping a client that requires it.
5. Preserve Capacitor as rollback during TestFlight migration.
6. Use minimum-supported-build response only after the native release path is proven.
7. Never remove old API/schema surfaces until Web and the latest supported native versions no longer depend on them.

Database migrations use expand-migrate-contract. Every migration must pass both a fresh local database and an upgrade copy/fixture before Staging. Production rollback defaults to forward repair when a destructive rollback would lose data.

The first combined E2E run found a navigation race: an Inbox polling component could hard-replace the current URL with `/inbox` while a tab navigation was in flight. Route-departure guards were added to Inbox and chat realtime refresh components.

A later repeated run exposed a second real race after a successful login response. Auth forms called `router.push(destination)` and immediately called `router.refresh()`, so the refresh could re-render `/login` before the push committed. Authentication transitions now use one `router.replace(destination)` call. The shared login test helper also validates the HTTP response before waiting on navigation. Three repeated chat plus standard-flow runs passed after the fix.
