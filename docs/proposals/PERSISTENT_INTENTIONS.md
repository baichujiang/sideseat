# 我的意愿：取消固定有效期

状态：修改方案，尚未实现或发布。
日期：2026-09-12。
代码基线：`891b627`，`feat/native-ui-design-system`。

## 1. 产品目标

“我的意愿”记录用户最近想做的具体事情。用户可以先表达意愿，找到愿意一起做的人后再约时间。

采用以下规则：

- 新意愿默认不填写时间，没有 14 天有效期，持续保留至用户移除。
- 保存新意愿即请求自动寻找，保存前说明“保存后会持续帮你寻找搭子，你可以随时暂停”。沿用现有一次保存流程。
- 暂停只停止寻找，卡片仍保留。修改暂停中的意愿不恢复寻找。
- 具体日期和时段是可选偏好；双方确认计划时再确定实际时间。
- “最近”是日常表达，不表示筛掉超过若干天的记录，也不新增定期续期或确认任务。

## 2. 页面与卡片

保留 Together 现有“推荐 / 我的意愿 / 探索”导航及分页交互。

页面标题使用“最近想做的事”，说明为“先记下想做的事，时间可以之后再商量。”；新增入口为“添加意愿”。

卡片信息由上至下：

1. 活动图标、具体事情名称；省略与名称重复的类别文字。
2. 用户填写的补充说明或必要课程信息；没有内容就不占行。
3. 可选时间偏好，例如“偏好：这周末下午”。未填写时整行省略。
4. 一行简洁寻找状态，例如“正在找搭子”或“已暂停寻找”。正常状态不再逐卡重复长说明。
5. 寻找状态所在行同时提供明确展开箭头和“管理意愿”的无障碍名称；展开后提供“暂停寻找 / 恢复寻找”和“编辑”，更多菜单提供“移除意愿”。默认不逐卡平铺操作按钮。

移除“有效至……”和“再保留 14 天”。探索公开设置仍位于编辑页，开启时卡片显示“已在探索公开”，默认私密状态不重复占行。

卡片按创建时间倒序排列；新建后回到“我的意愿”并定位新卡片。编辑、暂停和恢复保持原顺序及滚动位置。暂停的事情仍属于这份清单，不单独沉到列表底部。

空态：“最近想做什么？” / “写下一件事，我们帮你寻找愿意一起做的人。” / “添加意愿”。

### 视觉修订：沿用 Together 主题

2026-09-12 根据用户反馈，替换初版示意中没有来源的灰绿色配色。颜色以当前工作区 `SideSeatTheme.Together` 和 `docs/DESIGN_SYSTEM.md` 为依据；复用现有 `ActivityArtwork-*` 与 BrandMark 资源。

- 顶部采用森林绿导航底色，浅色页面标题和紧凑品牌标识。三个任务标签带对应图标，当前项使用浅柠檬色实底，拉开选中与未选中层次。
- 页面使用现有奶油色画布。运动卡为淡青柠色、咖啡卡为杏色、学习卡为浅蓝色，其余类别也严格使用现有固定映射；深色模式使用对应的深调色面。
- 卡片采用既有 22pt 圆角与细边界，标题配原有分类插画；说明、可选时间和操作区各有清楚层次。新增、保存使用已有墨色/浅色主操作配对。
- 颜色表示活动类别，寻找状态用明确文字表示；不以卡片颜色暗示匹配质量或承诺。
- 实施时直接消费共享主题颜色和组件，不在功能页另写一套近似颜色。当前修订仅更新方案与交互示意，不修改正在进行的原生主题代码。

### 交互深化：轻量列表与就地管理

目标是让用户打开页面时先看到自己想做的事，执行操作时再出现对应控件。后续“是否保留有效期”的建议仍为完全取消新意愿的有效期；意愿无到期倒计时、续期操作或自动过期状态，推荐的有限决定窗口独立保留。

- 默认卡片改为温暖的中性色面，分类色主要出现在插画区域及细边界。保留“整面淡色”的可比较方案，两者均使用相同主题颜色，不添加新的随机色系。
- 导航提供明确选中态，默认用浅柠檬色下划线随选择移动；原实色胶囊作为对照方案。标签点击与横向分页指向同一选择，无首尾循环，不干扰纵向滚动。
- 卡片中的事情、补充说明、可选时间和状态始终可读。点状态/管理行展开对应操作，同一时刻展开一张；关闭后仍保留状态文字。展开箭头、无障碍展开状态与实际可操作区域同步。
- 暂停后卡片留在原位，插画适度降低饱和度，状态显示“已暂停寻找”。提示提供“撤销”，其业务含义为显式恢复寻找；它不会重新激活暂停时已经失效的推荐。
- “添加一件想做的事”集中为列表后的一个主操作；编辑和新增从底部展开同一表单，背景页面保持上下文。真实 iOS 交付使用既有原生 sheet 及键盘避让。
- 保存前不创建意愿、不开始寻找；保存后关闭输入面板，回到“我的意愿”。新卡片在顶部出现并短暂强调，编辑继续保持卡片原顺序。取消关闭草稿，不触发保存。
- 后续执行更新（2026-09-12）：真人探索卡的“感兴趣”复用推荐页的双向选择机制，直接创建或关联同行机会，两个页面同步状态，双方独立感兴趣后进入聊天；不再打开新意愿表单，也不启用自动匹配。只有明确标注的示例卡保留“创建类似意愿”。详见 [Preview 55 发布记录](../releases/2026-09-12-explore-mutual-interest-preview55.md)。
- 动效基准：导航/页面切换约 220–240ms，卡片展开约 240ms，面板进入约 260ms、退出约 160ms。变化跟随用户操作，不播放持续跳动、呼吸或自动轮播动画。
- Reduce Motion 使用即时状态变化；按钮触区至少 44pt，弹层关闭后焦点返回原入口，展开区域关闭后不可被辅助功能误操作。

交互示意中的其他任务页仅用于说明导航连贯性；其中的清单和探索内容均为演示数据。原生行为、触感、键盘与完整数据链路需实施后按第 8 节验收。

## 3. 创建与编辑

将当前“活动 → 时间”的两步表单改成一个可滚动的表单。

| 字段 | 默认与行为 |
| --- | --- |
| 想做什么 | 必填，保留活动分类及现有具体活动、运动、学习目标输入 |
| 补充说明 | 可选；保留现有文字长度规则 |
| 课程 / 学习方式 | 只在学习类意愿需要时显示，沿用现有字段 |
| 添加时间偏好 | 默认折叠；可选择大致日期或具体时段，并可移除偏好 |
| 在探索公开 | 默认关闭，沿用当前服务端功能开关 |
| 底部操作 | 新建为“保存意愿”；编辑为“保存修改” |

填好活动必填信息即可保存，无须展开时间偏好或进入第二步。未填时间继续提交 `UNDECIDED` 和空 `timeWindows`。

已有时间偏好进入编辑页时直接显示；不会因编辑其他文字而丢失。移除时间偏好是显式操作。新意愿的日期选择不再受意愿 14 天寿命限制；具体时段仍需是未来的有效时间，沿用现有时长、数量、重叠和时区校验。

保存前的说明按状态显示：

- 新建或已参与寻找的意愿：“保存后会持续帮你寻找搭子，你可以随时暂停。”
- 暂停中的意愿：“保存后仍保持暂停，恢复寻找由你决定。”
- 未参与寻找的旧意愿：保存按钮附近明确说明保存会开始寻找，延续现有单次保存行为。

## 4. 状态和时间规则

| 状态 / 操作 | 我的意愿 | 新推荐和探索 | 已有聊天与计划 |
| --- | --- | --- | --- |
| 正在寻找 | 保留卡片 | 按现有匹配、公开设置参与 | 沿用现有规则 |
| 暂停寻找 | 保留卡片，可编辑、恢复、移除 | 停止新推荐，撤销该意愿未完成的推荐，退出探索 | 保留 |
| 恢复寻找 | 原卡片恢复状态 | 立即触发一次匹配 | 保留 |
| 移除意愿 | 从当前列表移除 | 结束寻找并处理待决定推荐 | 保留 |
| 系统暂不可用 | 保留卡片，显示准确状态 | 不声称系统正在寻找 | 沿用现有规则 |

“移除意愿”沿用当前结束确认流程，映射到 `ENDED`，保留必要历史关联。确认文案说明移除会停止寻找，已有聊天和计划继续保留。本次不新增归档中心、完成统计或新的“已完成”状态。

时间偏好过去后，意愿仍在，寻找授权仍然有效：

- 保留用户原始输入；卡片标注“原时间偏好已过去，可调整”。
- 匹配解释为尚未提供当前时间偏好，不把过去的时段显示成未来共同空闲。
- 对具体时段列表，只使用仍有效的时段；全部过去时适用上一条。
- 不自动改写成新的周末或日期，不自动清除原始输入。
- 编辑无关文字可原样保留旧偏好；主动修改时间时校验新的未来时间。

当前 discovery-first 将时间差异作为相关性信息，不是硬性排除条件；本次沿用这个规则。明确时间冲突仍如实显示，未知时间不计算虚构的重合时间。

意愿与推荐的期限独立：无固定活动时间的推荐仍在 48 小时内失效；具体时间推荐继续在相关时间前失效。推荐过期不结束意愿，后续符合条件时仍可出现新推荐。现有拒绝、冷却、阻止和未完成配对限制继续生效；不会因无有效期反复绕过这些限制。

形成或完成一次计划不自动移除意愿，例如用户可能仍然想继续打羽毛球。用户决定何时暂停或移除。

## 5. 已有数据

不批量将过去 14 天的寻找授权改为无限期，也不自动恢复已结束或已过期的意愿。

- 已有 ACTIVE 意愿：在原授权期限内继续寻找。用户在新版明确保存后转为长期意愿。
- 已有 PAUSED 意愿：仍暂停；新版保存可改为长期保留，但不会恢复寻找。用户主动恢复时按新版说明转为长期寻找。
- 上线时仍有效、之后按旧规则到期的意愿：新版清单保留记录并显示“寻找已停止”；用户可通过“继续寻找”的编辑/保存流程确认转换。它不能显示为正在寻找。
- 上线前已经 EXPIRED 或 ENDED 的记录：本次不重新加入当前清单。
- 旧版新建意愿：保留该版本的期限与授权契约，直到用户在新版明确转换。
- 时间偏好、探索公开选择和已形成的历史上下文全部保留，不通过迁移生成新授权。

为准确区分“原本已经结束”与“新版清单中应保留的旧记录”，迁移为当前仍有效的 ACTIVE / PAUSED 行设置下述 `retainedInMyIntentions` 标记；迁移不改其期限或匹配状态。判断“仍有效”同时检查状态和原截止时间，不能只看尚未被清理的 ACTIVE 状态。

## 6. 实现范围

### 数据和 API

建议 `WeeklyIntent.expiresAt` 改为可空：`null` 表示没有自动到期时间，非空保留旧契约；内部名称继续使用 WeeklyIntent，避免无关的大规模重命名。

新增 `retainedInMyIntentions Boolean @default(false)`，用于当前清单保留范围，不参与寻找授权。新长期意愿设为 true，迁移按第 5 节标记仍有效的旧记录。当前清单读取“仍有效的旧记录，或已标记保留且未 ENDED 的记录”；避免把整个历史全部重新展示。

新版明确新建/转换为长期意愿的请求，需要携带持久意愿能力标记及显式生命周期选择；服务端不能仅凭客户端版本在 GET 或普通旧请求中转为长期授权。新请求按既有幂等性、版本号和所有权规则处理。

旧 EXPIRED 记录仅在 `retainedInMyIntentions=true` 且用户在新版明确确认时允许转换；复用相同 ID，增加版本号，重新检查可参与条件。不复活已经失效的推荐、拒绝状态或旧配对，历史快照保持原样。

### 服务端联动

- `lib/v2/weekly-intents.ts`：新建、编辑/转换、恢复、当前列表和旧记录到期处理；长期行不执行自动到期。新界面移除 EXTEND，旧有期限记录保留旧客户端契约。
- `lib/v2/intent-timing.ts`、`weekly-intent-policy.ts`、`discovery-fit.ts`：解除寿命与偏好绑定；无日期直接计算未定时间上下文，不构造无限长日历窗口。日期区间兼容计算使用区间交集及日段规则，避免继续逐日展开任意长范围。推荐 TTL 单独计算。
- `lib/v2/mutual-opportunities.ts`：候选读取及事务内复核均接受无截止日期的有效 ACTIVE 意愿；保留参与授权、隐私及现有配对约束。
- `lib/v2/explore-intents.ts`：无截止日期行可按公开选择参与，处理过去的偏好与响应中的可空字段。
- `lib/v2/together-matching-session.ts`：保留已安装旧客户端停止寻找的效果，确保也能暂停新的长期意愿。
- `lib/validators/weekly-intent.ts`、API 路由和 `openapi/v1.json`：生命周期输入、可空输出、错误文案和契约一致。

现有服务端对 ACTIVE / PAUSED 的 12 条保护阈值保持；迁移保留的已停止旧记录不占匹配行名额。用户触及现有边界时可移除不再想做的事情，本次不新增产品配额或无限清单承诺。

### 原生客户端

- `TogetherRootView.swift`：精简卡片、单页编辑器、可选时间入口、移除延期入口、排序与旧意愿继续寻找。
- `WeeklyIntentModels.swift`、`WeeklyIntentStore.swift`：可空截止时间、新生命周期请求、清单保留状态、有效时间显示。
- `ExploreIntentModels.swift` / `ExploreIntentListView.swift`：同步可空字段和时间说明。
- 从 OpenAPI 重新生成 Swift 客户端；手写模型同步。更新中文、英文和德文文案及相关 UI 测试。
- 落地时更新 PRODUCT、TOGETHER_CONTRACT、FLEXIBLE_INTENT_TIMING 与 INTENT_DRIVEN_MATCHING 文档，以本方案最终实现替代相冲突的 14 天规则。

## 7. 兼容与 Preview 交付

当前安装记录中的普通版为 41，Preview 为 45，当前 Swift 模型将 `expiresAt` 解码为必填 Date。可空响应需要先解决客户端契约，不能直接向旧客户端发送 null。

建议按以下次序交付：

1. 本地隔离数据库实现并验证迁移、接口和新旧客户端行为。
2. 发布支持可空模型的后端，长期意愿创建由单一发布开关控制，初始关闭；为新客户端暴露能力。
3. 安装能够读取新旧字段的 Preview，完成本地完整链路验收；真实后端尚未支持时，新交互不能伪装成长期保存成功。
4. 内部测试客户端完成兼容更新后，再启用长期创建能力。服务端仅接受新版明确的长期授权请求。
5. 对遗漏的旧客户端，遇到含长期意愿的相关意愿/探索读取，使用现有错误信封给出明确的升级提示；不返回伪造截止时间。旧版停止寻找以及可识别记录的暂停/结束操作继续生效。
6. 记录源码 commit、迁移/部署版本、Preview build 和验收结果，供真机反馈对应版本。

如需回退，先关闭新的长期创建/转换，继续保留读取可空字段和处理已存在长期意愿的服务端能力；不把已授权的长期意愿强行改成 14 天，也不直接回滚到无法读取 null 的旧服务端。

Preview 目前连接生产 API。真机完整验收需要可访问的新后端；纯本地改界面不能证明生产已取消有效期。实施阶段先准备完整可审查的部署变更，再按当时的发布授权完成部署。本方案本身不执行部署、数据迁移、Git 推送或真机安装。

## 8. 验收

1. 输入一件想做的事，不填写时间，一次保存后出现卡片并进入现有自动匹配流程。
2. 使用注入的服务端时间推进 15 天、30 天，长期意愿仍保留并具备寻找资格；模拟器模型显示与服务端一致。
3. 真实本地双账号链路：两个未填写时间的长期意愿 → 推荐 → 双方同意 → 聊天 → 提出并接受带明确时间的计划 → 双方日历。
4. 暂停后卡片仍保留，不新增推荐；编辑保持暂停；恢复后立即尝试寻找。
5. 移除后退出列表及候选池，已有聊天、已确认计划和日历投影保留。
6. 可选时间保存/清除正确；偏好过去后保留原数据并如实显示；不虚构共同空闲，不阻止无关文字编辑。
7. 推荐自身依然按原决定窗口过期；到期不会使长期意愿消失，也不会绕过拒绝和未完成配对限制。
8. 旧 ACTIVE / PAUSED / EXPIRED / ENDED 各状态按迁移方案验证；仅明确保存/恢复能延长寻找授权。
9. OpenAPI 与 Swift 解码验证旧的日期值和新的 null；旧客户端获得明确升级结果，停止寻找仍有效。
